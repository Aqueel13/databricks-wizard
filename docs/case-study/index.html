Overview

The problem. Every large company has the same supplier entered several times. It appears as a vendor in the ERP, a supplier in the procurement tool and a profile in the supplier portal. Regional buyers type names in their own scripts. Until those records agree, spend per supplier is split, delivery performance can't be compared, and a certificate's expiry date in the portal drifts from the actual PDF. An AI assistant asked about a supplier either can't see this data or sees it without governance.

The approach. Databricks Wizard fixes this at the data layer:

  • it resolves every source record into one golden supplier;
  • it governs that data in Unity Catalog;
  • it gives analysts (Genie, a dashboard), data stewards (a review app) and AI agents (three MCP servers) the same tables and metric definitions.

The scenario. Larkspur Foods is a fictional food manufacturer with company codes in the US, the Netherlands, Poland and Ukraine. Its supplier names come from public procurement records, so the matcher faces real spelling variety: Polish diacritics, Ukrainian Cyrillic and inconsistent transliteration. A generator plants the problems a real company has and writes every one into an answer key. Every quality claim on this page is therefore measured, not estimated.

One supplier, three systems, two scripts: ТОВ "АФІНА-КОН" in SAP company code UA01, AFINA-KON, LTD in Coupa, AFINA-KON, TOV in HICX. The matcher links all three, keeps the local-script name and stores the evidence for each link.

How it works

Land safely

Data is written before its manifest, and offsets are committed last. A crash can re-send data but never lose it. Bronze checks every file against its manifest.

Clean and check

Change events are applied in source order, so late and out-of-order updates land correctly. Bad rows are quarantined with the rules they failed, not dropped.

Resolve

Normalization, a probabilistic model, embeddings and a guarded LLM build one golden supplier, and every link keeps its evidence.

Serve

Facts, KPIs, risk and Supplier 360 are keyed on that supplier. Unity Catalog metric views define each KPI once, for Genie, the dashboard and agents alike.

Entity resolution

This is the core of the project. The layers run in order, and each one handles what the one before it can't settle:

  1. Normalize.
    • Legal forms in five languages are stripped and kept as their own attribute (ТОВ = Sp. z o.o. = LLC).
    • Names are transliterated to Latin and reduced to a phonetic skeleton.
    • National IDs (EIN, NIP, EDRPOU) are validated with their checksums.
  2. Link the certain pairs. Equal valid IDs, or exact names in the same country with nothing contradicting them, link immediately.
  3. Score the rest. A Splink (Fellegi–Sunter) model trained without labels compares names at several levels, plus IDs, city, legal form and numbers inside names. Multilingual embeddings add candidate pairs that share no characters.
  4. Ask an LLM about the uncertain middle. Pairs with a match probability of 0.50–0.95 go to Qwen3-Next 80B, which returns a verdict with a reason.
  5. Cluster with constraints. No merge is allowed across different valid IDs, jurisdictions or clearly different cities. Refused links go to a steward queue.

The LLM made results worse until it was guarded. Unguarded, it matched one record to several suppliers and chained their clusters together, and F1 fell. Treating "matches many" as ambiguity rather than identity fixed it.

Stewards review the queue in a Databricks App. Their decisions win over every automated layer and are recorded under their name. The golden record keeps its full history (SCD type 2).

Documents

Contracts and ISO certificates, including scanned ones, are processed in four steps:

  • They are parsed with ai_parse_document.
  • Fields are extracted with one strict JSON schema per document type.
  • The extracted fields are compared with what HICX and Coupa say.
  • When a certificate PDF disagrees with the supplier portal, the PDF wins and the risk score moves.

Questions about documents are answered from page-level chunks, and every answer cites [file, page]. A question that names a document number is answered by exact lookup first, because embeddings treat CTR-00247 and CTR-00248 as nearly identical.

Agents and people

Three MCP servers (analytics, knowledge and stewardship) run on one Databricks App. They mirror Intelligence WatchDog's split, so one agent can use both systems the same way.

  • Every tool returns provenance: the SQL run, the tables read and the pages cited.
  • Every call is logged under the caller's identity.
  • An agent can propose a steward decision, but only a person can approve it.
  • A sanctions alert is a name similarity for review. No tool presents it as a finding.
  • WatchDog polls a feed of suppliers whose delivery performance has started to deteriorate.

Governance

  • Masks: bank accounts and national IDs are masked in the catalog for anyone outside the stewards group, agents included. A health check fails the job if a PII-tagged column is unmasked.
  • Row filter: invoices are scoped by company code. A Poland-only identity sees only PL01 invoices.
  • Lineage, end to end: every metric traces through Unity Catalog lineage to SAP, Coupa and HICX tables. Sampled rows trace further, to the landing file and the shipper manifest that declared it.
  • Least privilege: CI deploys as its own service principal. It can change code but not the identity jobs run under. WatchDog has its own principal, which can only call the MCP app.

Models chosen by benchmark

Four benchmarks on the same platform picked three different models.

  • Qwen3-Next 80B adjudicates matches (0.92 accuracy, no false non-matches) and runs the agents.
  • Llama 4 Maverick extracts document fields best, but often writes tool calls as plain text, so it isn't used for agents.
  • For names, only the multilingual Qwen3 embedding does anything across scripts.

Limitations

  • The sources are mocks fed by a generator. Supplier names are real, but the company, its transactions and its documents are fictional.
  • Sanctions screening against the public OFAC list demonstrates the workflow. It is not a compliance control.
  • Free Edition has workspace groups only, so table grants go to each service principal rather than to groups. Apps also stop after 24 hours, and a daily compute quota applies.
  • Financial risk is not assessed: no financial data source was loaded.

Key design decisions

Push, not pull

A shipper with manifests gives at-least-once delivery and reconciliation from day one.

Real names, planted problems

Real procurement names give realistic variety, and a generated answer key makes every claim measurable. Builds are byte-for-byte reproducible.

Govern in the catalog

Masks and filters live in Unity Catalog, not in app code, so every path (SQL, Genie, agents) obeys them.

MCP for agents

Typed, audited tools that return provenance, with governed tools preferred over free-form SQL.

Build story

Problems found and fixed along the way

  • The answer key was wrong before the matcher was
    SAP training copies of one vendor were grouped inconsistently, so no matcher could score well. Fixing the key without touching the data (checksums verified) was worth more than any tuning.
  • A planted problem nobody could detect isn't a test
    The first delivery-drift storyline sat inside real-data noise. It was redone at a realistic size, and the rule was made market-adjusted, because the market's on-time rate swings between 31% and 77% month to month. The rule also found real declines in the untouched SAP history.
  • A missing tool, not a weak model
    Every model failed the spend-concentration question by writing broken SQL. One governed tool fixed it for all of them.
  • Name-only screening alerts too often
    It raised 82 alerts for 6 planted near-matches. OFAC addresses showed that most alerts had a country conflict, so those are now cleared automatically when the name isn't near-exact.
  • The deploy permissions trap
    Declaring permissions in an Asset Bundle makes the deployer the owner of every job, which only an admin may do. CI was fixed by granting access once, outside the bundle.
